1. Plain-language overview & the problem we solved

Imagine a clinician has a folder with a progress note, a lab spreadsheet, a chart image, a voice recording and a short procedure video. Asking one question across all of them is hard because every file has a different format. A normal chatbot can only “read” text, and if you paste a table or a caption into it, the answer is not traceable back to the source.

MedReason solves this in five steps:

  1. Ingest each file with the right tool (document parser, Pandas, VLM, ASR, frame sampler).
  2. Normalise everything into one structure — an EvidenceChunk containing text, a modality tag, a source reference (page / row / timestamp) and a vector embedding.
  3. Retrieve the most relevant chunks for a question using hybrid similarity.
  4. Generate an answer with an LLM that is explicitly told: “use only this evidence, cite it as [E1], and say when it is insufficient.”
  5. Inspect — the UI shows the exact snippet behind every citation.
The central idea is grounding. The assistant is not a medical knowledge base. It is an evidence-navigation layer. If the uploaded records do not contain the answer, the correct behaviour is to say so — not to invent a diagnosis.

What “intelligent decision support” means here

When the user enables Decision Brief, the system retrieves evidence and asks the text model for a strict JSON report: executive summary, findings, quantitative metrics, alternatives with pros/cons/feasibility/risk, mitigations, a recommendation and next steps. The frontend renders this as a structured report card. If no model is configured, the system does not fabricate clinical advice — it returns an honest evidence inventory.

5. Data model & unified evidence index

The schema has six tables. FileRecord tracks uploads, DocumentChunk keeps legacy document chunks, EvidenceChunk is the unified multimodal retrievable unit, Conversation/Message store chat history, DecisionReport stores structured reports, and StoredBlob holds upload bytes for serverless deployments.

Figure 3 — All modalities converge on one evidence table; source references preserve traceability.

5.1 Anatomy of an EvidenceChunk

{
  "file_id":      "uuid-of-upload",
  "chunk_index":  3,
  "modality":     "dataset | document | image | audio | video",
  "source_ref":   "Row 4"  /  "Page 2"  /  "12s-18s"  /  "00:04",
  "text":         "Lab/table record: Hemoglobin_g_dL=14.8, TSH_mIU_L=1.8 ...",
  "embedding_json":"[0.012, 0.084, ... 768 floats]",
  "metadata_json": "{ ... modality-specific fields ... }"
}

Why this matters: because images, audio and video are converted to text descriptions with timestamps, the same retriever, the same ranking function and the same citation renderer work for all five modalities. No separate “image search” or “video search” subsystem is needed.

6. End-to-end request flow

Figure 4 — Retrieval happens before generation; citations are built from the same chunks used in the prompt.

6.1 The seven steps inside OrchestrationService.handle_user_message()

  1. Ensure a conversation exists (create from first 40 characters of the message if needed).
  2. Persist the user message with its modality and file IDs.
  3. Route to the decision path if the toggle is on or the text asks for decision support.
  4. Retrieve evidence first — top 4 chunks across all uploaded files.
  5. Add deterministic tabular calculations as extra [E#] evidence (never bypass retrieval).
  6. Call the LLM with a grounded system prompt containing the evidence block.
  7. Persist and return the assistant message with sources and metadata (charts, grounded flag).
Key design choice: dataset answers are added to the evidence context, not used as a shortcut response. This preserves one pipeline for every modality and keeps the LLM's answer auditable.

8. Hybrid retrieval algorithm

Retrieval is implemented in VectorRepository.search_evidence(). It combines semantic similarity with lexical term overlap so that both “meaning” and exact clinical terms (e.g. Hemoglobin_g_dL) influence ranking.

Figure 6 — Deterministic hybrid ranking; no external vector database or paid embedding API.

8.1 Why these weights

  • Dense (0.75): captures paraphrase — “heart rate reading” matches “heart rate 96 bpm”.
  • Lexical (0.25): protects exact tokens such as column names, patient IDs and timestamps that hashing vectors can blur.
  • Hashing vectorizer: 768 dimensions, L2-normalised, n-grams 1–2. Stateless, so query and document vectors are always comparable and no fitted model file can drift.

8.2 Citation construction

# build_citations(): every retrieved chunk becomes a citation object
Citation(
  source_id  = chunk.id,          # internal [E#] identity
  filename   = file_rec.filename, # human-readable source
  row_or_item= chunk.source_ref,  # "Page 2" / "Row 4" / "00:04"
  snippet    = chunk.text[:220],  # exact supporting text
  relevance_score = chunk.score   # retrieval score
)

The UI uses the same list to render citation chips and the Evidence Inspector, so the “[E1]” in the answer and the snippet shown to the user come from the same object — no post-hoc invented references.

10.1 app/config.py — one source of truth for settings

# Environment-driven; safe defaults so the app runs with no keys
LLM_PROVIDER   = os.getenv("LLM_PROVIDER", "mock")

# Local directory creation is wrapped in try/except because serverless
# filesystems are read-only outside /tmp.
if STORAGE_BACKEND != "database":
    for p in [DATA_DIR, UPLOAD_DIR, ...]:
        try: p.mkdir(parents=True, exist_ok=True)
        except OSError: pass

Why: every service reads these settings instead of hardcoding values, so the same code runs locally with SQLite and on Vercel with Postgres simply by changing environment variables.

10.2 services/storage_service.py — serverless-safe uploads

def save(content, filename, subfolder) -> str:
    if backend == "database":
        insert StoredBlob(data=content) ; return f"blob:{blob.id}"
    else:
        write to backend/data/uploads/<subfolder> ; return file path

def resolve(path_or_key) -> str:
    if key starts with "blob:":
        load StoredBlob ; write bytes to /tmp/medreason/<id>_<name> ; return path
    return path  # local development path already readable

Why: Vercel's filesystem is ephemeral. Storing bytes in Postgres and materialising them per request lets the existing document/Pandas/OpenCV/ASR processors keep using ordinary file paths — a small abstraction instead of rewriting every service.

10.3 repositories/vector_repo.py — indexing and retrieval

add_evidence_chunks(file_id, chunks)
  → embed texts → insert EvidenceChunk rows (text, vector, modality, source_ref)

search_evidence(query, file_ids, top_k, threshold)
  → query_vec = embed_query(query)
  → for each chunk:
       dense   = cosine(query_vec, chunk_vec)
       lexical = Σ IDF(term) over matching query terms, normalised
       score   = 0.75*dense + 0.25*lexical
  → filter by threshold, sort desc, return top_k

build_citations(results) → filename + source_ref + 220-char snippet + score

Why: this is the heart of RAG. Keeping indexing, scoring and citation construction in one class means the context given to the LLM and the citations shown to the user can never diverge.

10.4 services/orchestrator.py — routing and synthesis

chunks = vector_repo.search_similar_chunks(query, file_ids, top_k=4)
context_blocks = [f"[E{i}] {filename} ({source_ref}, {modality}): {text}" ...]

# Dataset calculations are appended as evidence, not returned directly
for ds in dataset_files:
    ans = data_analysis_service.answer_question(ds.file_path, ds.filename, message)
    context_blocks.append(f"[E{len+1}] {ds.filename} (dataset computation): {ans['answer']}")

answer = await llm_service.generate_response(message, context="\n".join(context_blocks))

Why: a single orderly pipeline for all modalities. Decision support is routed before retrieval because it needs its own JSON schema; everything else shares the grounded-answer path.

10.5 services/decision_support_service.py — honest decision reports

chunks   = vector_repo.search_evidence(query, top_k=6, threshold=0.06)
context  = "[E1] ... [E6] ..." + tabular metrics
generated = await llm_service.generate_json(prompt, context) if context else None

if generated:
    return _coerce_report(generated, ...)   # Pydantic-validated, disclaimer injected
else:
    return _fallback_report(...)            # evidence inventory, never clinical advice

Why: strict JSON makes the report machine-checkable. The fallback names its “alternatives” Evidence path 1/2/3 rather than inventing treatments — critical for an academic clinical demo.

11. Grounding, citations & decision reports

11.1 The grounding contract

  1. The LLM receives evidence as [E1] … [En] with filename and source reference.
  2. The system prompt forbids unsupported medical facts and requires an explicit “insufficient evidence” statement.
  3. Citation chips in the answer map to Citation objects returned with the message.
  4. The Evidence Inspector displays filename, source reference, snippet and relevance score.
  5. The academic disclaimer is appended in the prompt requirement and enforced in report coercion.

14. Safety, ethics & limitations

Academic demonstration only — not for clinical use. All records are synthetic. The app is not a medical device, is not validated, and must never inform patient care.

Safety mechanisms built into the system

  • Disclaimer in the UI top bar, every answer prompt, report coercion and documentation.
  • Synthetic-only fixtures; README warns against real patient data.
  • Grounded system prompt + explicit “insufficient evidence” behaviour.
  • Offline decision mode never fabricates clinical recommendations.
  • Safe Pandas planner — no arbitrary code execution.
  • API keys in environment variables; `.gitignore` excludes `.env`; secret scan before commit.

Limitations to state honestly

  1. Answers are limited to uploaded evidence, which may be incomplete or mis-ranked.
  2. Image captions and transcripts are machine-generated metadata, not verified observations.
  3. Video uses interval frame sampling, not continuous temporal modelling.
  4. Tesseract and Whisper are optional; fallbacks are lower fidelity.
  5. SQLite/local files suit demonstration; Vercel requires hosted Postgres.
  6. Hobby function timeout prevents live LLM calls; Pro is needed.

15. Presentation Q&A cheat sheet

Q: What exactly is the “multimodal” part?
Five input types — text documents, structured tables, images, audio and video — are each processed by a specialised extractor, then normalised into the same EvidenceChunk format so one retriever and one citation system handle all of them.
Q: Is this a medical chatbot that gives diagnoses?
No. It is an evidence-navigation and report-generation prototype. It answers only from uploaded synthetic evidence, cites every claim, and explicitly says when evidence is insufficient. It carries an academic-only disclaimer throughout.
Q: Where does the RAG happen?
In VectorRepository.search_evidence(): embed the query, score every chunk with 0.75 cosine + 0.25 IDF lexical overlap, take the top-k, and pass those chunks to the LLM as [E1]…[En].
Q: Why HashingVectorizer instead of OpenAI embeddings?
It is free, deterministic, stateless and needs no model download or API key. Query and document vectors are guaranteed to live in the same space across restarts.
Q: Which AI models are used?
Groq qwen/qwen3.8-27b for text and structured JSON; Gemini gemini-flash-lite-latest for vision; optional Whisper for speech; scikit-learn hashing for embeddings; OpenCV/Pandas/Pillow for local processing.
Q: Why did you change the model names?
The original names were retired on the providers. We queried the live /models endpoints and selected currently available free-tier IDs. This is documented in the README.
Q: What happens if the API key is missing?
The app still works. Text generation uses a deterministic grounded mock, image analysis uses local OpenCV statistics, and decision support returns an evidence inventory instead of invented advice.
Q: How do citations stay honest?
The same chunk objects produce both the [E#] context for the LLM and the Citation objects for the UI. Each citation carries filename, source_ref, snippet and score, so it can be checked against the original file.
Q: Why add dataset calculations to the evidence instead of answering directly?
So every modality follows one pipeline. A Pandas result becomes another cited [E#] chunk; the LLM still synthesises the final answer, and the exact calculation is shown separately.
Q: How is decision support different from chat?
It requests strict JSON conforming to a Pydantic schema and renders alternatives, risks and next steps as a report card. Chat returns free-form grounded Markdown with citations.
Q: What happens on Vercel's free tier?
The whole app runs with offline providers. Live Groq/Gemini calls take up to 45s and exceed the ~10s Hobby limit; upgrade to Pro and set maxDuration=60 to use them.
Q: Why Postgres on Vercel?
SQLite files and local uploads do not persist across serverless invocations. Postgres stores the database and upload bytes; storage_service stages bytes into /tmp only for the current request.
Q: How do you prevent fabricated medical advice in offline mode?
The fallback report names “evidence paths”, states that no synthesis was available, lists risks and assumptions, and never claims a clinical effect.
Q: What did you verify before submitting?
9/9 integration tests, a successful production frontend build, a simulated serverless run, live-provider smoke tests and a secret scan.
Q: What would you add next?
Cross-encoder reranking, hosted object storage for media previews, temporal video models, a proper evaluation set for answer faithfulness, and role-based access — still with synthetic data only.
